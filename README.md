# Starter Kit — Final Exam: Local RAG for Programming

โปรเจคนี้**ทำงานได้ตั้งแต่ยังไม่ได้เขียนโค้ดสักบรรทัด** ส่วนที่เป็นระบบ เช่น API, Docker, การเชื่อมต่อ Ollama และการจัดการ error เตรียมไว้ให้ครบแล้ว
หน้าที่ของนักศึกษาคือเขียนฟังก์ชันใน `student/` ให้ระบบตอบได้ดีขึ้น

```
starter/
├── core/          🔒 ห้ามแก้ (ระบบส่งงานตรวจ checksum ถ้าถูกแก้จะไม่รับงาน)
├── Dockerfile     🔒 ห้ามแก้
├── student/       ✏️ เขียนโค้ดที่นี่ ค้นหาคำว่า TODO HERE
│   ├── chunking.py    1. แบ่งเอกสารเป็นชิ้น
│   ├── embedding.py   2. แปลงข้อความเป็น vector
│   ├── retrieval.py   3. ค้นหาชิ้นที่เกี่ยวข้องกับคำถาม
│   ├── prompts.py     4. prompt สำหรับตอบข้อสอบ และเขียนโค้ด
│   └── settings.py    ค่าที่ปรับจูนได้ (ขนาด chunk, top-k, hybrid …)
├── manifest.json  ✏️ ใส่รหัสนักศึกษาและชื่อ
├── requirements.txt ✏️ เพิ่ม library ได้ (ห้ามลบของเดิม)
└── tools/
    ├── doctor.py      🩺 ตรวจทุกอย่างก่อนส่ง แล้วสร้าง zip ให้
    ├── selfcheck.py   ทดสอบ API กับชุดตัวอย่าง
    └── pack.py        สร้าง zip (doctor เรียกให้อัตโนมัติ)
```

## ระบบทำงานอย่างไร
```
ระบบส่งเอกสาร ──▶ chunking.split ──▶ embedding.embed_documents ──▶ เก็บไว้
ระบบถามข้อสอบ ──▶ retrieval.make_query ──▶ embedding.embed_query ──▶ retrieval.search
              ──▶ prompts.build_mc_prompt ──▶ LLM ──▶ คำตอบ ก–จ
ระบบให้เขียนโค้ด ──▶ prompts.build_code_prompt ──▶ LLM ──▶ โค้ด Python ──▶ รัน unit test
```
- ฟังก์ชันที่ยังเป็น `pass` จะใช้**ค่าตั้งต้นที่ไม่ได้แก้ปัญหาอะไรเลย** ระบบยังรันได้และตอบถูกรูปแบบ แต่คะแนนเกือบ 0
  - ข้อสอบปรนัย: ไม่เรียก LLM ตอบ "ก" ทุกข้อ
  - โจทย์โค้ด: ได้ฟังก์ชันว่างที่ไม่ผ่าน test
  - chunking, embedding และ retrieval: ไม่แบ่ง ไม่มี vector และไม่ส่งเอกสารให้ LLM
  - **ทำ `prompts.py` ก่อน** เพราะถ้ายังไม่ทำ ส่วนอื่นจะไม่มีผลต่อคะแนนเลย
- ถ้าฟังก์ชันของคุณ error ระบบก็จะใช้ค่าตั้งต้นแทน service จึงไม่ล่ม และ log จะบอกว่า error อะไร

## เริ่มต้น
1. ติดตั้ง Docker Desktop, Python 3.10 ขึ้นไป และ [Ollama](https://ollama.com) แล้วดาวน์โหลดโมเดล
   ```
   ollama pull qwen2.5-coder:7b
   ollama pull nomic-embed-text
   ```
2. แก้ `manifest.json` ให้ `student_id` และ `name` เป็นของตัวเอง (`llm_model` เลือกได้ `qwen2.5-coder:7b` หรือ `qwen2.5-coder:14b`)
3. รันครั้งแรกโดยยังไม่ต้องแก้อะไร
   ```
   docker compose up --build
   ```
   เปิด http://localhost:8000/health ที่หัวข้อ `student_functions` จะเห็นว่าแต่ละฟังก์ชันอยู่สถานะไหน (`todo` / `ok` / `error`)
4. เปิดอีกหน้าต่าง แล้วทดสอบกับชุดตัวอย่าง
   ```
   python tools/selfcheck.py
   ```

## ลำดับที่แนะนำ
ทำทีละไฟล์ แล้วรัน selfcheck ทุกครั้ง จะเห็นคะแนนขึ้นทีละขั้น
0. **`prompts.py` แบบง่าย ๆ ก่อน**: ส่งคำถามและตัวเลือก หรือโจทย์ ให้ LLM ระบบจะเริ่มตอบได้จริง (ยังไม่ใช้เอกสาร)
1. **`chunking.py`**: แบ่งตามหัวข้อ markdown แล้วตัดย่อยให้ยาวพอดี
2. **`embedding.py`**: เรียก `embed()` แล้วเติม prefix `search_document:` / `search_query:`
3. **`retrieval.py`**: คำนวณความคล้ายด้วย `cosine_many` แล้วเลือก top-k จากนั้นลองทำ hybrid search ต่อ
4. **`prompts.py` (ปรับต่อ)**: ใส่เอกสารที่ค้นได้ลงใน prompt และสั่งให้ยึดเอกสารเป็นหลัก ส่วนโจทย์โค้ดสั่งให้ตอบเป็น code block เดียว

เมื่อทำเสร็จแต่ละจุดให้**ลบบรรทัด `# TODO HERE: ...` ออก** และอย่าลืมลบ `pass`

ระหว่างพัฒนา ถ้าแก้โค้ดแล้วต้องรัน `docker compose up --build` ใหม่ทุกครั้ง
ดู log ได้ด้วยคำสั่ง `docker compose logs -f app` ถ้าฟังก์ชันของคุณ error จะขึ้นข้อความ `[student.xxx] เกิด error ...` ใน log

## แนวทางปรับจูน (tuning) — ต้องปรับอะไรบ้าง
ค่าที่ปรับได้รวมอยู่ใน **`student/settings.py`** แก้ทีละค่าแล้ววัดผลทุกครั้ง (ดูหัวข้อ "วิธีวัดผล" ด้านล่าง)

### 1. Chunking (`student/chunking.py`) — ผลต่อคะแนนมาก
| ปรับอะไร | ทางเลือก | หมายเหตุ |
|---|---|---|
| วิธีแบ่ง | ตามความยาว / ตามหัวข้อ markdown / ตามย่อหน้า | เอกสารในข้อสอบมีหัวข้อชัด การแบ่งตามหัวข้อมักได้ผลดีที่สุด |
| ขนาด (`CHUNK_SIZE`) | 300–1,500 ตัวอักษร | เล็กเกินไปบริบทขาด ใหญ่เกินไปความหมายเจือจาง และเปลือง context ภาษาไทยไม่มีช่องว่างคั่นคำ จึงควรนับเป็นตัวอักษร |
| ซ้อนกัน (`CHUNK_OVERLAP`) | 0–20% ของขนาด | ช่วยกรณีคำตอบอยู่คร่อมรอยตัด |
| ใส่หัวข้อแม่ใน chunk | `"Fenwick > การอัปเดต\n..."` | ช่วยมากกับคำถามที่อ้างชื่อหัวข้อ |
| โครงสร้างพิเศษ | ไม่ตัดกลางตาราง, code block หรือ list | ตารางที่ถูกตัดครึ่งทำให้ตอบคำถามเรื่องตัวเลขหรือปีผิด |

### 2. Embedding (`student/embedding.py`) — ผลปานกลาง
| ปรับอะไร | ทางเลือก |
|---|---|
| prefix | `search_document:` สำหรับเอกสาร และ `search_query:` สำหรับคำค้น nomic-embed-text ถูกฝึกมาแบบนี้ ถ้าไม่ใส่ คุณภาพจะลดลงชัดเจน |
| ข้อความที่นำไปทำ embedding | เนื้อหาอย่างเดียว / ใส่หัวข้อด้วย / ใส่ชื่อเอกสารด้วย |

ข้อจำกัด: **เปลี่ยนโมเดล embedding ไม่ได้** และ `nomic-embed-text` เด่นภาษาอังกฤษ การค้นภาษาไทยจึงไม่แม่นเท่า ข้อ 3 จึงสำคัญ

### 3. Retrieval (`student/retrieval.py`) — ผลต่อคะแนนมาก
| ปรับอะไร | ทางเลือก | หมายเหตุ |
|---|---|---|
| คำค้น (`make_query`, `QUERY_WITH_OPTIONS`) | คำถามอย่างเดียว / คำถาม + ตัวเลือก / ค้นแยกทีละตัวเลือกแล้วรวมผล | คำตอบมักอยู่ในย่อหน้าที่มีคำของตัวเลือกที่ถูก |
| จำนวน (`TOP_K`) | 3–10 | มากไปจะมีเอกสารไม่เกี่ยวปนมาจน LLM สับสน น้อยไปอาจไม่เจอคำตอบ |
| **Hybrid search** (`HYBRID_WEIGHT`) | คะแนน vector + คะแนน keyword (นับคำที่ตรงกัน หรือ BM25) | **ช่วยมากที่สุดกับภาษาไทย ชื่อเฉพาะ และตัวเลข** ซึ่ง embedding มักจับไม่ได้ ใช้ library `rank-bm25` ได้โดยเพิ่มใน `requirements.txt` |
| Re-ranking | ให้ LLM ให้คะแนน chunk ที่ค้นได้ แล้วเลือกเฉพาะที่ตรงจริง | แม่นขึ้นแต่ช้าลง ระวังเวลา 90 วินาทีต่อข้อ |
| กรอง/ขยายผล (`MIN_SCORE`) | ตัด chunk ที่คะแนนต่ำ / ดึง chunk ข้างเคียงมาด้วย | ช่วยกรณีคำตอบอยู่กระจาย 2 chunk |
| ตัดซ้ำ | ถ้ามี chunk ที่เนื้อหาซ้อนกันมาก ให้เหลือตัวเดียว | ประหยัดพื้นที่ context |

### 4. Prompt (`student/prompts.py`) — ผลต่อคะแนนมาก
| ปรับอะไร | ทางเลือก |
|---|---|
| grounding | สั่งว่า "ยึดเอกสารเป็นหลัก แม้ขัดกับความรู้ทั่วไป" สำคัญมาก เพราะเอกสารบางชุดมีข้อมูลเฉพาะที่ต่างจากความรู้ทั่วไป |
| การจัด context (`MAX_CONTEXT_CHARS`) | ลำดับ (ชิ้นที่เกี่ยวข้องที่สุดอยู่ต้นหรือท้าย), ติดหมายเลขหรือชื่อแหล่งที่มา, จำกัดความยาว |
| ภาษาของ prompt | อังกฤษ / ไทย / ผสม ข้อสอบเป็นภาษาไทย ลองทั้งสองแบบแล้ววัดผล |
| คำถามเชิงปฏิเสธ | เน้นย้ำเมื่อคำถามมี "ไม่", "ยกเว้น", "ผิด" |
| ให้คิดก่อนตอบ | ให้เขียนเหตุผล (`reason`) สั้น ๆ ก่อนเลือกคำตอบ ระบบบังคับรูปแบบ JSON ให้อยู่แล้ว |
| prompt โค้ด | ย้ำ signature, ใช้เฉพาะ standard library, ทำตามข้อห้ามในโจทย์, ให้ตรวจกับตัวอย่างในโจทย์ก่อนตอบ |

### ค่าที่ระบบล็อกไว้ (ทุกคนได้เท่ากัน)
`temperature = 0`, context 8,192 token, รูปแบบคำตอบ JSON, การดึงโค้ด และการขอแก้โค้ด 1 รอบเมื่อ compile ไม่ผ่าน ทั้งหมดอยู่ใน `core/` แก้ไม่ได้

### วิธีวัดผล
1. **แก้ทีละอย่าง แล้ววัดทุกครั้ง** ด้วย `python tools/selfcheck.py` จดผลไว้ว่าแต่ละการเปลี่ยนแปลงทำให้คะแนนขึ้นหรือลงเท่าไร
2. **สร้างชุดทดสอบของตัวเอง** ชุดตัวอย่างมีแค่ 6 ข้อ เล็กเกินกว่าจะเห็นความต่าง
   - คัดลอก `tools/sample_pack/` เป็นโฟลเดอร์ใหม่ แล้วใส่เอกสารยาว ๆ (เช่น lecture note ของรายวิชา) ใน `knowledge/`
   - แต่งคำถามเพิ่มใน `mc.json`
   - รันด้วย `python tools/selfcheck.py --pack <โฟลเดอร์>`
3. **ดู `sources` ทุกครั้งที่ตอบผิด** (selfcheck แสดง และดูได้จากผลของ `/ask`)
   - ถ้า chunk ที่มีคำตอบ**ไม่อยู่ใน** sources แปลว่า chunking หรือ retrieval มีปัญหา
   - ถ้า**อยู่แล้วแต่ยังตอบผิด** แปลว่า prompt มีปัญหา
4. **ระวังเวลา** ทุกเทคนิคที่เรียก LLM เพิ่ม (re-rank, multi-query, ถามซ้ำแล้วโหวต) จะช้าลง `/ask` ต้องตอบภายใน 90 วินาทีต่อข้อ
5. **ขอตรวจในระบบอย่างมีแผน** ขอได้แค่ 5 ครั้ง ให้รวมการปรับหลายอย่างที่วัดด้วย selfcheck แล้วว่าดีขึ้น ก่อนกดขอตรวจแต่ละครั้ง

### ลำดับที่แนะนำ
chunk ตามหัวข้อ → ใส่ prefix → cosine top-k → prompt ที่ยึดเอกสาร → **hybrid search** → ปรับ `TOP_K` และ `CHUNK_SIZE` → re-rank (ถ้ายังมีเวลา)

## กติกา
- ห้ามแก้ `core/` และ `Dockerfile` ถ้าต้องการโค้ดเพิ่ม ให้สร้างไฟล์ใหม่ใน `student/`
- ตอนตรวจ**ไม่มีอินเทอร์เน็ต** library ทั้งหมดต้องอยู่ใน `requirements.txt` และห้ามดาวน์โหลดอะไรตอนรัน
- เรียก LLM และ embedding ได้เฉพาะผ่าน `core.ollama_client` ด้วยโมเดลที่ระบุใน manifest
- เขียนไฟล์ได้เฉพาะ `/tmp`
- `/ask` ต้องตอบภายใน 90 วินาทีต่อข้อ ระวังอย่าเรียก LLM หลายรอบเกินไป
- ห้าม hard-code คำตอบ ถ้าตรวจพบจะได้ 0 ทั้งงาน
